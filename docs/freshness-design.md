# Automated feed freshness

SSR listings, detail pages and the sitemap use a bundled snapshot when the provider rejects Worker egress. Refresh the snapshot independently of Worker deploys and keep a complete version available through collection failures. Browser refresh continues to fetch the provider directly.

## Priority and scope

Sourcing leads and freshness follows. The measured feed had 471 iframes on one host, unreachable from the research network for the full session even while the API answered. Each source carries only `name`, `default`, `type` and `data`. A fresher listing cannot restore playback during a host outage. This design works with the current feed and requires no sourcing changes to implement or test. [Sourcing baseline and provider fields](sourcing-research.md)

The proposed runner probe checks the directory API for reachability. Sourcing §4 probes embed and playback health. Both can reuse runner setup, host identity derived from the source URL, and generic timeout and logging helpers where applicable. Keep the playback probes in sourcing and reuse their results there for ranking. Feed publication depends on directory completeness and does not fetch embed pages, manifests or media segments. [Sourcing reliability measurement](sourcing-research.md#4-reliability-measurement)

## Options and rollout gates

| Option | Decision |
| --- | --- |
| GitHub Actions schedule | Use a best-effort five-minute pilot on standard GitHub-hosted Linux x64. Five minutes is the minimum. Load can delay runs by 5–15 minutes in the planning model or drop them altogether. Public-repo inactivity can disable the schedule after 60 days. Use one concurrency group for schedule and manual runs, with running-job cancellation disabled. Under default queue behavior, a newer queued run replaces the pending run. [Schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) · [Concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) |
| Cloudflare Cron or external scheduler hitting a Worker route | One-minute Cron expressions are possible. Account for overlap and monitor gaps independently. A scheduler calling a route still uses blocked Worker egress and costs one dynamic request per call. A full sample poll also exceeds the Worker Free 50-subrequest limit. An external collector with approved provider access can be evaluated separately if Actions misses the target. Its cadence, overlap and missed-run behavior need measurement. [Cron](https://developers.cloudflare.com/workers/configuration/cron-triggers/) · [Worker limits](https://developers.cloudflare.com/workers/platform/limits/) |
| Snapshot plus full build/deploy, or deploy with only assets changed | Full deployment always makes about 212 provider calls and takes an estimated 2–5 runner minutes. Reusing a build artifact saves the build, but the asset manifest still belongs to a Worker version and activating it requires deploy credentials. Recurring deploys also expose the site to the 503s reported in the brief. [Worker static assets](https://developers.cloudflare.com/workers/static-assets/) |
| Snapshot to KV | At ~213 writes for per-endpoint files plus a pointer, Free stops at four complete publications/day. A packed value fits the write budget at five minutes if within 25 MiB, but requires reading and parsing the whole value. Separate keys introduce propagation skew and more reads. [KV limits](https://developers.cloudflare.com/kv/platform/limits/) · [KV consistency](https://developers.cloudflare.com/kv/concepts/how-kv-works/) |
| Snapshot to private Standard R2 | Use one packed object with byte ranges and a small manifest. R2 provides strongly consistent reads and avoids recurring deployments and snapshot bytes in the Worker JavaScript bundle. [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/) · [R2 binding](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) |

1. **Provider access and budget come first.** Before building the integration, the repository owner clears a single low-volume `GET /streams` probe with the provider from the proposed Linux runner, with no retry or detail fan-out. Runner reachability is unverified and one success proves only that run. After the probe, obtain an approved sustained rate, burst/concurrency limit and daily budget for both lists and details. [API.md](../API.md) allows at most one `/streams` poll per 60 seconds and states no aggregate detail budget. A 212-call collection needs more than 53 requests/minute within a four-minute job once startup, validation and upload take time. Pace requests across all endpoints with the approved limits, at most four concurrent detail requests, and stop before the deadline. Stop the project at this gate if access is denied, unconfirmed, or the budget cannot support one complete paced collection. Increasing the poll interval lowers daily volume but leaves the per-job requirement.
2. **Repository and infrastructure ownership.** There is no remote. The repository owner creates the public GitHub Free repo after reviewing the history for secrets, publishes `main` as the protected default branch, and configures `feed-production` with a `main`-only branch rule and no manual approval on scheduled runs. Public Free supports those environment controls and standard hosted runner minutes are free. The Cloudflare account owner authorizes R2 activation within the Standard free allowance, provisions private `kwip-feed-prod` and `kwip-feed-preview`, and owns the `INFRA.md` update moving R2 out of “Not yet” as part of implementation. `CONTRACT.md` currently gives that file no owner. [GitHub environment rules](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments) · [Actions billing](https://docs.github.com/en/actions/concepts/billing-and-usage)
3. **Acceptance before rollout.** Run a week of approved preview collection. Measure listing and detail freshness separately from upstream observations through canonical SSR, including scheduling gaps, collection, and the 30-second HTML TTL plus potential 300-second stale-while-revalidate. Aim for healthy-cycle single-digit minutes and report p50, p95, max and missed polls. A five-minute schedule supplies no bounded freshness guarantee. Detail-only changes may remain unseen indefinitely until a list hash changes. Compare a provider-approved sample of details independently in preview. If that blind spot or measured age misses the owner's target, hold rollout and agree on a detail collection budget or upstream change signal. Routine detail audits are deferred.

## Collection and atomic publication

- Add an opt-in runner mode in `scripts/snapshot-feed.mjs`, invoked as `node scripts/snapshot-feed.mjs --publish-r2`. Keep `pnpm snapshot` for the bundled seed and existing rollback path. Fetch the two lists, validate schema and paths, then SHA-256 hash each list with stable object-key ordering and preserved array order. Exclude envelope `timestamp` and `performance` from the hash. Keep viewer counts in the hash initially. Normal activity can therefore make most polls count as changed.
- On bootstrap or a list hash change, collect every distinct detail, retaining all-or-nothing behavior. Validate detail IDs against the requested keys and reject invalid or unexpectedly empty lists. If an empty collection is legitimate, review it with the provider before accepting it. A malformed response, 5xx, block, deadline or partial collection leaves the previous generation and verification unchanged.
- Pack validated public endpoint JSON into `snapshots/<commit-id>.bin`. A manifest at `current.json` contains the schema version, unique commit ID for this attempt, payload key, object size, endpoint byte offsets and lengths, hashes, and verification and publication times. Preserve original provider timestamps in the payloads. Use S3 `PutObject` via the AWS CLI on the runner. Create the immutable payload with `If-None-Match: *`. Replace the manifest with `If-Match` against the ETag read before collection, or `If-None-Match: *` on bootstrap. The successful manifest write commits the generation. The same manifest precondition applies to unchanged polls.
- A timeout can occur after either write commits. For an ambiguous payload PUT, read back the intended key and compare content length and SHA-256 before proceeding. Retry an absent payload only with the same create precondition. For an ambiguous manifest PUT, GET `current.json` and compare the commit ID and expected contents. A match means success. If the original ETag still holds, or the original key is still absent for bootstrap, retry only under the original precondition. A different generation or a failed precondition means another writer won. Stop and let the next poll collect against the winner. If reconciliation cannot finish within the job deadline, report unknown outcome and let the next run read the authoritative manifest first. [R2 S3 conditional operations](https://developers.cloudflare.com/r2/api/s3/api/)
- On unchanged hashes, skip details and the packed-object PUT. Still write the manifest once to record a successful list check and new commit ID while retaining the payload reference and original publication time. The verification time is operational metadata. It does not refresh the visitor's stale clock.

## Reader, freshness and CPU

1. Bind `FEED_SNAPSHOTS` in `wrangler.toml` and resolve Cloudflare binding access in `nuxt.config.ts`. Pass a structural reader to `server/utils/feed.ts`. Update SSR consumers through `app/composables/useFeed.ts` and wire `server/routes/sitemap.xml.ts` to the same adapter. Use R2 only for configured external feeds on Workers. Preserve fixtures, ping and the unbound Node path. Keep the existing `ASSETS` binding and bundled seed. No new runtime dependency.
2. Pin a generation for the whole SSR response, sharing one request-scoped manifest read across parallel consumers. Validate schema version, key and ID formats, bounds, offset and length arithmetic, expected identities, success wrappers and supported source URL schemes before rendering. Reuse host substitution and `fromCache` provenance. A valid manifest that omits an endpoint is authoritative. Show that detail unavailable. If a generation is unreadable and the seed is eligible, retry the entire response's feed requirements against the seed before any payload is serialized. If a whole-response retry cannot be made, render unavailable. Never fill an individual hole from another generation. The sitemap omits unavailable entries and can return an empty valid sitemap.
3. Keep `fetchBrowserFeed` and the post-hydration mount refetch. Start it for absent SSR payloads as well as cached ones. For live and VOD details with unavailable cached data or a missing cached endpoint, render a mountable unavailable page with the canonical URL and no player. Avoid a fatal SSR 404 that prevents recovery. Upgrade in place when the direct fetch returns a valid matching detail. Keep existing true 404 handling for definitive invalid routes and retain the client’s previous-payload and bundled-asset fallbacks. No public snapshot or health routes. Preserve mirror redirects, canonical and Open Graph URLs, and the link/embed contract.
4. Preserve the shipped `useFeedFreshness.ts` semantics. Show the bar at the existing 20-minute threshold from the feed's origin timestamp and retain the existing receive-time fallback when origin is absent. An unchanged manifest leaves the origin unchanged. Acknowledge the visible bar only after a successful uncached retry of every required payload. If any payload is absent or marked `fromCache`, the bar remains eligible to show. No separate detail stale clock.
5. Benchmark the largest listing, detail and sitemap on a preview Worker with representative payloads and cold reads. Measure CPU for manifest parsing, range decoding, validation, host substitution and SSR together against the Free 10 ms CPU limit. Record bundle size, read counts, CPU p95 and worst observed CPU. Require headroom below 10 ms on all three before rollout. Range reads reduce I/O and still leave parsing and substitution on the same CPU budget. Check `pnpm test`, `NITRO_PRESET=node-server pnpm build`, `pnpm build` and `pnpm exec wrangler deploy --dry-run`. Inject authoritative omission, missing seed, partial range errors, uncertain PUT outcomes and concurrent commits in preview. [Worker limits](https://developers.cloudflare.com/workers/platform/limits/)

## Daily costs and free-tier headroom

Assume 210 details plus two lists on changed runs, two lists on unchanged runs and no routine detail audit. Runner minutes are estimates at 1–2 billed minutes per snapshot job. Public standard runner compute is free at every supported Actions interval.

| Interval | Polls/day | Provider calls/day unchanged / changed | Runner min/day | R2 PUTs/day unchanged / changed | KV per-endpoint writes/day changed |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 min, external comparison | 1,440 | 2,880 / 305,280 | 1,440–2,880 equivalent | 1,440 / 2,880 | 306,720 |
| 5 min | 288 | 576 / 61,056 | 288–576 | 288 / 576 | 61,344 |
| 10 min | 144 | 288 / 30,528 | 144–288 | 144 / 288 | 30,672 |
| 15 min | 96 | 192 / 20,352 | 96–192 | 96 / 192 | 20,448 |

- Worker Free provides 100,000 dynamic requests/day. The publisher uses zero site Worker requests. At 50,000 feed-bearing invocations/day, about 50,000 remain before redirects, other dynamic traffic, monitoring and preview. KV Free includes 100,000 reads/day, 1,000 writes/day and 1 GB storage. A manifest plus two KV payload reads would reach the read cap near 33,333 such invocations/day. KV Paid overages are $0.50/million reads and $5/million writes after included usage. [Worker limits](https://developers.cloudflare.com/workers/platform/limits/) · [KV pricing](https://developers.cloudflare.com/kv/platform/pricing/)
- Standard R2 includes 1 million Class A operations, 10 million Class B operations and 10 GB-month monthly, shared across the account. At five minutes, budget up to 17,280 publication PUTs and 17,280 baseline publisher GETs in 30 days for the manifest and backoff check, plus reconciliation and cleanup. One manifest GET and up to two range GETs per feed-bearing invocation implies up to 4.5 million Class B operations per 30 days at 50,000/day, or 9 million at the Worker cap. Count additional endpoint reads if sitemap or another route exceeds that model. Include preview, cleanup and monitor traffic before rollout. Above the allowance, posted rates are $4.50/million Class A, $0.36/million Class B and $0.015/GB-month, with free egress. Operate within the allowance. [R2 pricing](https://developers.cloudflare.com/r2/pricing/)
- R2 storage is the average of daily peak bytes, measured in decimal GB-month. At 1 MiB per generation, seven days of five-minute changes plus up to one day of cleanup lag yields about 2.42 GB peak per bucket or 4.84 GB for identical production and preview. At one minute even seven days in one bucket is 9.85 GiB or approximately 10.57 decimal GB before lag and preview. Measure actual snapshot sizes and peak bytes in both buckets, including failed uploads and other account storage. Start preview with manual runs only. Keep the committed payload indefinitely. Once per day under the same writer serialization, prune unreferenced payloads older than seven days with the existing publisher credential. Budget list operations and monitor cleanup lag. Pause publication or reduce retention before breaching the free allowance. [R2 storage billing](https://developers.cloudflare.com/r2/pricing/)

## Failures, secrets and rollback

| Condition | Behavior |
| --- | --- |
| Unchanged or complete poll | Serve the current committed generation. Record run outcome, schedule delay, duration, request count and commit ID. |
| Provider 5xx, shape change, partial details or rejected publish | Keep serving the last committed generation. Transient failures wait for the next normal poll. On 429, record `retryNotBefore` in a private `backoff.json` key from `Retry-After` or the approved backoff. Each run checks that key before contacting the provider. On explicit block, set a manual hold in the same key and alert the repository owner to disable the workflow pending provider resolution. Treat a failed read of existing backoff state as a failed run. If the hold cannot be written, page the owner to disable the workflow and cancel pending runs. No automatic burst retries. A KV quota error in the alternative also leaves the previous publication current. |
| Scheduler missing or persistent failure | The independent monitor checks Actions run history and last successful publish/check, including unchanged polls. Alert the repository owner after 30 minutes without a successful verification. A read-only R2 check can verify the committed manifest and one referenced list range are available. Bucket timestamps can be forged by the writer and are only an availability signal. The visitor bar still uses the original feed freshness rules. |
| R2 unreadable or absent | Use the bundled seed as a whole-response fallback. If it is unavailable, serve a valid mountable unavailable page and let the browser try the provider directly. |

Use `.github/workflows/feed-refresh.yml` with a four-minute timeout, `contents: read`, pinned actions, protected `main` and an environment-scoped R2 S3 key pair. Scope the R2 Object Read & Write token to the production bucket only. Preview uses its own bucket-scoped key. The job receives zero Worker deployment or DNS credentials. A compromised runner can still replace, delete or fabricate the entire feed and its timestamps. Reader validation limits malformed payloads and unsupported URLs, but cannot verify the truth of a structurally valid feed. The bundled seed is outside the publisher's reach. The KV alternative would need account-level `Workers KV Storage Write` and no Workers deployment permission. [R2 token permissions](https://developers.cloudflare.com/r2/api/tokens/) · [KV permission](https://developers.cloudflare.com/api/resources/kv/subresources/namespaces/subresources/values/methods/update/)

1. The repository owner disables the workflow and cancels running and queued jobs. The Cloudflare account owner revokes the publisher credentials immediately. The repository owner deletes production and preview environment secrets.
2. The Cloudflare account owner restores the recorded pre-integration Worker version using Wrangler rollback. The repository owner reverts the integration commit so the next release retains the bundled path and the original deploy command.
3. The deployment owner verifies the bundled seed exists in the restored version and serves coherent listing and detail data, plus the sitemap, browser recovery and mirror redirects. After verification the repository owner retires the freshness monitor and associated read credentials.
4. Keep both buckets isolated during incident review. After a seven-day rollback window and issue closure, the Cloudflare account owner archives any needed evidence and deletes both buckets once no retained deployment references them.
