# Fix — task 52, enrichment must never abort a refresh

Review at `scripts/collect-publish-feed.mjs:320`. Reproduced with the live feed: the same 2,097,142-byte
detail publishes with exit 0 when the scoreboard is empty, and with exit 1 `Score enrichment exceeded file
limit` when it matches. Enrichment is optional; a valid refresh must never die for it.

Make the pack step shed enrichment instead of throwing:

1. Before measuring, collect every changed record that actually carries a `match` now. Sort them by the byte
   growth that record would add — largest growth first.
2. Walk them largest first and, while `bytes.length > fileLimit` for that record, or the running `size` would
   reach `snapshotLimit`, drop `match` from that record: delete it from `payload.data`, delete it from the
   shared listing item (the `byPath`/`streamListing` entries built just above), and remove the record from the
   changed set if it has no other change.
3. Only re-serialise and re-hash records that still carry a change after shedding.
4. Count what was shed in `result.scores.shed` so it is visible in the run log; a shed match simply renders as
   today's row downstream.
5. Keep the existing hard failures for a record that was already over the limit before enrichment, and for
   the 40 MiB snapshot only after shedding has run out of things to shed.

Tests: a detail just under the limit plus a match that pushes it over publishes and logs `shed: 1` with no
`match` on that item; a match that fits keeps it; `shed` is 0 when nothing was shed; the listing item loses
its `match` in step with its detail.

Gate: full suite, both builds, default rebuild, dry-run, and a live collector dry run of the case that failed
(empty scoreboard must still publish, matching scoreboard must publish with `shed` ≥ 1). Commit, don't deploy,
don't touch `.prompts` or `DECISIONS.md`.
