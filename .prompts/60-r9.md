# Task 60, round nine — make the parity oracle sensitive again

`/tmp/60-review8.log`, approve with nits plus one limitation. Layout is done and must not change: margin 20.5 %, hero
fill 82.4 %, no clipping, no regressions. Everything here is the test oracle and the doc.

What the review established:

- The decoder mechanics are right, but **67.5 % is a calibration constant fitted to this fixture**, not an edge
  definition; the engines want different values (Chromium improves past 77.5 %, WebKit is best near 65 %) and the
  residuals have **opposite signs by line** (WebKit DPR 4: state −0.62 device px, scores +0.40). The 1.3 device px
  tolerance then absorbs the bias.
- That loosening is new: DPR 2 was 0.5 CSS px in round seven and is now 0.65. At DPR 2 Chromium cannot see a −0.4 CSS
  px model error in any row, and a detail-line error of 0.5 CSS px (the edge that sets the gap) passes in every row,
  both engines, in the minus direction. At DPR 4 a one-device-pixel shift *upward* fails only 3/32 Chromium rows.
- The controls run at DPR 4 and one direction only, and the end-of-engine assertion needs just one failing row, so
  63/66 falling to 1/66 would pass.

The point of parity is to catch a **model** error big enough to matter (Times is ~0.9 CSS px), not to model AA. So
subtract the bias instead of tolerating it:

1. **Bias-corrected residual.** For each line and edge, take the signed `model − pixel` residual, subtract a per-
   engine/DPR/line reference bias, and assert the corrected residual against a tight bound — target 0.4 CSS px at
   DPR 4 and 0.3 CSS px at DPR 2, which is now finer than the current 0.65. Measure the reference bias on the
   committed build and record how it was obtained (per line, per engine, per DPR) and how stable it is between runs.
   If a per-line reference is unstable, say so with numbers and use the per-engine/DPR value instead.
2. **Keep an uncorrected absolute bound too**, so bias correction cannot hide a gross shift: the current 1.3 device px
   stays as the outer bound and the corrected one is the inner.
3. **Controls at both DPRs and both directions**, and gate the count, not one row: every control class must fail at
   least 90 % of its rows, otherwise the gate fails. Expect the one-device-pixel control at DPR 2 to be weak (it is
   0.5 CSS) — say what it should be per DPR rather than keeping a flat device figure.
4. **Two missing asserts** from the review: the plate is empty before measuring (all ink hidden), and the ink does not
   touch the first or last clip row.
5. **Doc:** 67.5 % is a calibration constant with the per-engine fit range and residual signs; a sensitivity table per
   DPR and direction, corrected and uncorrected; and the honest statement of what stays undetectable (opposite-sign
   per-line errors, ~1.9 device px relative in WebKit).

Do not retune layout values. Gate: full matrix, 199 tests, both builds, dry run, commit, do not deploy.
